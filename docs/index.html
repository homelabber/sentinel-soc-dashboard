The Problem

Every SOC has too many screens and not enough overview

Sentinel has workbooks. Defender has its portal. XDR has its own dashboard. Each tool shows a slice of what is happening, and none of them show the full picture in a way you can glance at from across the room.

We wanted one screen on the wall that answered the questions the team asks every morning: How many incidents came in overnight? Who has the oldest open ticket? Are we above our ingestion threshold? Any High alerts right now?

The constraint that shaped the entire design: no backend server to maintain. No Node.js process to babysit, no database to back up, no VM to patch. Something that just works, refreshes itself, and does not need an engineer to keep alive.

Context Infrastructure teams in healthcare are lean. Every piece of tooling that needs active maintenance is a liability. If the dashboard breaks on a Sunday night during an incident, nobody wants to debug a server — they want to work the incident.

Architecture

Two Logic Apps, one blob container, one HTML file

Two Logic Apps run on a 5-minute schedule, query Sentinel via the Log Analytics REST API using Managed Identity, and write the results as plain JSON to Azure Blob Storage. The dashboard — a single HTML file — fetches those blobs with fetch() and renders everything client-side.

Microsoft Sentinel (Log Analytics workspace) │ │ POST /query · HTTP action · Managed Identity ▼ Azure Logic Apps (Consumption · every 5 minutes) │ │ PUT application/json · Managed Identity ▼ Azure Blob Storage ├── incidents.json 24h new incidents ├── open-incidents.json all open assigned tickets ├── age-distribution.json open M/H/C for age chart └── metrics.json ingestion · heartbeat · alerts │ │ fetch() every 5 minutes ▼ dashboard.html (browser · any device · any screen)

Why Managed Identity instead of API keys

Both Logic Apps authenticate using their System Assigned Managed Identity. No secrets. No API keys stored in the Logic App JSON. No credentials that expire, rotate, or leak in a Git commit. The only setup is assigning IAM roles once: Log Analytics Reader and Storage Blob Data Contributor.

We specifically avoided API connectors (the drag-and-drop ones in Logic Apps Designer) because they require OAuth connections that need periodic re-authorisation. Managed Identity via raw HTTP actions is more work to set up but never breaks.

Why Blob Storage instead of a database

The dashboard only needs to read data — it never writes anything back. Blob Storage is the simplest possible read endpoint: a URL that returns JSON. No connection strings, no SDK, no authentication headers. Just fetch(). The trade-off is last-write-wins with no history, which is fine for a live operational view that wants current state, not archives.

KQL — Lessons Learned

The queries that took the longest to get right

Getting Sentinel incident data right is harder than it looks. SecurityIncident is an audit log — every change to an incident creates a new row. A single incident touched 50 times today has 50 rows, all with TimeGenerated set to the time of each change.

Filter before summarize — the most important performance fix

If you filter after arg_max, the query scans all of history before applying your where clause. On a workspace with years of incident data this causes silent timeouts inside Logic Apps — returning 1 or 2 results with no error message. That is exactly what we saw for weeks before finding the root cause.

// ✗ Slow — scans entire history, then filters
SecurityIncident
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| where TimeGenerated > ago(24h)

// ✓ Fast — pre-filters rows, then summarizes
SecurityIncident
| where TimeGenerated > ago(24h)
| where CreatedTime > ago(24h)
| summarize arg_max(TimeGenerated, *) by IncidentNumber

CreatedTime vs TimeGenerated

TimeGenerated is updated every time an incident is touched — by playbooks, correlation rules, or an analyst adding a comment. Filtering on it for a "24h new incidents" view gives you incidents modified today, not created today. On a busy day this inflated our count from ~50 real new incidents to 90+ rows. The fix is one extra line:

where CreatedTime > ago(24h)

The analyst workload query needs no time filter

For a true picture of what each analyst currently has on their plate, you want the current state of every open assigned incident — regardless of when it was created. Some incidents are weeks old. A time filter hides them entirely.

// All open assigned incidents — ground truth for analyst workload
SecurityIncident
| summarize arg_max(TimeGenerated, *) by IncidentNumber
| where Status != 'Closed'
| where isnotempty(Owner.userPrincipalName)
| project IncidentNumber, Title, Severity, Status,
  CreatedTime, Owner=tostring(Owner.userPrincipalName)
| order by CreatedTime asc
Watch out Sentinel has multiple owner fields: Owner.assignedTo, Owner.userPrincipalName, Owner.email. Which one is populated depends on your Entra ID configuration and how incidents are assigned. In our environment Owner.assignedTo was empty for most incidents while Owner.userPrincipalName had the UPN. Check yours in Log Analytics before hardcoding the field name.

The age distribution query

For the age chart we use arg_max on LastModifiedTime and exclude Low and Informational to focus only on actionable incidents:

// Open incident age distribution — Low, Medium, High only
SecurityIncident
| summarize arg_max(LastModifiedTime, *) by IncidentNumber
| where Status != 'Closed'
| where Severity !in('Informational', 'Low')
| project IncidentNumber, Title, Severity, Status,
  CreatedTime, LastModifiedTime,
  Owner=tostring(Owner.userPrincipalName)
| order by LastModifiedTime desc

Deployment

From zero to live dashboard in an afternoon

  1. Create a Storage Account and Blob container Any tier works. Add a CORS rule: Allowed origins *, methods GET, max age 86400. Set container access level to Blob for public anonymous read and for security reasons apply a IP Filter!
  2. Deploy the Incidents Logic App Create a Consumption Logic App, enable System Assigned Managed Identity, open Code view, paste logicapps/logicapp-incidents.json. Replace the placeholders: workspace ID, storage account name, container name.
  3. Deploy the Metrics Logic App Same process using logicapps/logicapp-metrics.json. This one handles ingestion stats, agent heartbeat, top alerts, and sign-in summary.
  4. Assign IAM roles to both Managed Identities On the Log Analytics workspace: Log Analytics Reader + Microsoft Sentinel Reader. On the storage account: Storage Blob Data Contributor.
  5. Run both Logic Apps manually to verify Check the run history — all actions should be green. Then check your blob container: four JSON files should appear within seconds.
  6. Configure dashboard.html and open in Chrome Set the BLOB constant at the top of the script block to your storage URL. Open the file in Chrome, press F11 for fullscreen. Mount on wall.
~€2
Estimated monthly Azure cost Logic Apps Consumption at ~€0.000025 per action. Two Logic Apps, 5-minute intervals, ~10 actions each = roughly €1–2/month. Blob storage for a few KB of JSON per write is negligible.
Better architecture Replace the public blob with Azure Static Web Apps (free tier). This avoids needing public read access on the container and lets you add authentication so only your team can view the dashboard. The Logic Apps stay exactly the same. But: users have to log in again after a while (token expiry, session timeout, or browser closure).

What to improve or add

Azure Static Web Apps. Currently the container needs public read access. Static Web Apps is free, supports custom domains, and lets you add Entra ID authentication so only your team can reach the dashboard. Downside of that is reauthentication

A Teams alerting Logic App. A third Logic App that fires a Teams adaptive card when a High incident has been open for more than 2 hours without an owner. Straightforward to add with the same Managed Identity pattern.

Historical snapshots. Each Logic App run overwrites the previous blob. Appending a timestamped copy would enable 7/30/90-day trending charts without any additional infrastructure.

Forked from Jeroenvdbroek/sentinel-soc-dashboard This is a fork of Jeroenvdbroek/sentinel-soc-dashboard, which is the origin of the architecture and the dashboard described above. Everything on this page up to this point describes that original design. This fork keeps it and adds the following:
  • Azure Static Web Apps hosting with Entra ID authentication — listed above as future work. The blob container no longer needs public read access.
  • A direct-query API — an App Service backend that queries Log Analytics over managed identity (DATA_SOURCE=loganalytics), so the dashboard can run without the Logic App and blob hop. Blob mode still works and both modes return the same shape.
  • A Teams alerting Logic App — also listed above as future work. Adaptive cards for new Critical/High incidents and for SLA breaches at the moment they cross the threshold.
  • 30-day trend queries — incident volume, MTTR, SLA compliance and open backlog.
  • Microsoft Defender portal deep links — incident links resolve to security.microsoft.com via AdditionalData.providerIncidentUrl rather than the Azure portal Sentinel blade, which is unsupported after 2027-03-31.
